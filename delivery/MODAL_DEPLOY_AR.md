# نشر خدمة Quran-ARS على Modal — دليل خطوة بخطوة

> تم اختيار **Modal** بدلاً من RunPod Serverless بعد تحليل التكلفة: عند حِمل ~٢٥٠ تقييماً يومياً
> يكون Modal **أرخص** و**أسرع استجابةً**، لأن بدء التشغيل السريع فيه يسمح بإطفاء الـ GPU بسرعة
> دون أن يدفع كل طلب ثمن تحميل النموذج (١–٣ دقائق).
>
> **النتيجة النهائية:** رابط HTTPS عام (`https://<org>--quran-ars-web.modal.run`) تستجيب واجهته
> خلال أجزاء من الثانية، ولا تُحاسَبون على الـ GPU إلا أثناء تصحيح تلاوة فعلياً.

---

## ١) البنية المعمارية (لماذا هي رخيصة وسريعة معاً)

```
web()   — CPU فقط، صورة صغيرة، تبقى دائماً جاهزة (min_containers=1)
          /health, /ping        -> استجابة فورية
          /api/evaluate         -> تحقّق من المفتاح -> يُطلِق مهمة GPU -> {"status":"processing", jobId}
              │
              │  .spawn()  (مهمة مستقلة تكمل حتى النهاية بغضّ النظر عن انتهاء الطلب)
              ▼
Grader  — GPU (A10G)، يُحمّل نموذج NAMAA مرة واحدة لكل حاوية (@modal.enter)
          تنزيل الصوت -> تصحيح الكلمات والحركات -> رفع ملف mp3 إلى R2 -> إرسال الـ webhook
          ثم ينطفئ تلقائياً بعد ٦٠ ثانية من الخمول
```

نتيجتان مهمّتان:

- **الواجهة (API) لا تنتظر الـ GPU إطلاقاً.** يحصل المتصل على `jobId` فوراً حتى لو لم يكن هناك
  GPU يعمل — أي أن زمن الإقلاع البارد لا يؤثّر على الطلب، بل يؤخّر الـ webhook فقط.
- **الـ GPU يُحاسَب عليه فقط أثناء التصحيح.** عند ٢٥٠ تقييماً يومياً (~١٠ ثوانٍ لكل تقييم) يعني ذلك
  ~٢١ ساعة GPU شهرياً بدل الدفع مقابل وقت الخمول.

> هذا هو الحل للمشكلة التي جعلت RunPod مكلفاً: هناك كنّا مضطرين لمهلة خمول طويلة كي لا تُقتَل
> المهمة الخلفية، ما يعني الدفع مقابل GPU خامل طوال اليوم. أمّا `.spawn()` في Modal فتجعل المهمة
> وحدة عمل مستقلة لا تموت بانتهاء الطلب، فيمكن تقصير مدة الخمول بأمان.

---

## ٢) المتطلبات قبل البدء

- [ ] حساب على **Modal** ([modal.com](https://modal.com)) — يتضمّن رصيداً مجانياً شهرياً.
- [ ] مساحة تخزين **Cloudflare R2** (أو أي تخزين متوافق مع S3) لملفات الصوت — **إلزامية**،
      لأن حاويات Modal مؤقتة وتُمحى عند الإطفاء (القسم ٤).
- [ ] تثبيت الأداة محلياً: `pip install modal && modal token new`
- [ ] توليد مفتاح `AI_API_KEY` قوي (يُشارَك مع تطبيقكم):
      `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`

---

## ٣) إنشاء مساحة R2 (لملفات الصوت التوضيحي)

1. من لوحة Cloudflare → **R2 → Create bucket**، مثلاً باسم `quran-ars-audio`.
2. **R2 → Manage API tokens → Create** (صلاحية Object Read & Write) ← سجّلوا:
   **Access Key ID**، و**Secret Access Key**، و**Account ID**.
3. اجعلوها متاحة عبر نطاقكم: الـ bucket → **Settings → Public access → Connect custom domain**
   ← `cdn.quranyutla.com`.

بذلك تحصلون على:

| القيمة | مثال |
|---|---|
| `S3_ENDPOINT_URL` | `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` |
| `S3_BUCKET` | `quran-ars-audio` |
| `S3_PUBLIC_BASE_URL` | `https://cdn.quranyutla.com` |

---

## ٤) إنشاء الـ Secret في Modal

كل الإعدادات تُحقَن كمتغيّرات بيئة من Secret واحد اسمه **`quran-ars`** (يشير إليه `modal_app.py`):

```bash
modal secret create quran-ars \
  AI_API_KEY='<المفتاح-القوي>' \
  S3_BUCKET='quran-ars-audio' \
  S3_ACCESS_KEY_ID='<r2-access-key>' \
  S3_SECRET_ACCESS_KEY='<r2-secret>' \
  S3_ENDPOINT_URL='https://<ACCOUNT_ID>.r2.cloudflarestorage.com' \
  S3_PUBLIC_BASE_URL='https://cdn.quranyutla.com' \
  S3_PREFIX='feedback/'
```

> **لماذا R2 إلزامية هنا؟** لأن Modal يمسح قرص الحاوية عند الإطفاء، فأي ملف `feedback_*.mp3`
> يُكتَب محلياً سيختفي. عند ضبط هذه المتغيّرات ترفع الخدمة كل ملف وتُعيد رابطاً مثل
> `https://cdn.quranyutla.com/feedback/...` داخل الحقل `feedbackAudio`. وإن لم تُضبط فسيعمل الكود
> لكنه سيُرجع مساراً محلياً ينتج عنه خطأ 404 على Modal — لذا لا تتخطّوا هذه الخطوة.

## ٥) النشر

```bash
cd delivery
modal deploy modal_app.py
```

أول عملية نشر تبني الصورة و**تُضمِّن النموذج (٥ جيجابايت) بداخلها** (١٠–٢٥ دقيقة). عمليات النشر
اللاحقة تستخدم الطبقات المخزّنة وتستغرق ثوانٍ.

سيطبع Modal الرابط العام، مثلاً:

```
✓ Created web => https://<your-org>--quran-ars-web.modal.run
```

هذا الرابط هو ما تضعونه في `AI_SERVICE_URL` لدى الباك-اند.

---

## ٦) التحقّق من نجاح النشر

```bash
BASE=https://<your-org>--quran-ars-web.modal.run
KEY=<قيمة AI_API_KEY>

# ١) فحص الصحة — يجب أن يستجيب فوراً (حاوية CPU جاهزة دائماً)
curl $BASE/health
# {"status":"ok","service":"web","version":"2.0.0"}

# ٢) التأكد من رفض المفتاح الخاطئ
curl -s -X POST $BASE/api/evaluate -H "X-AI-API-Key: wrong" \
  -H "Content-Type: application/json" \
  -d '{"audioUrl":"https://x/a.mp3","surahNumber":112,"fromAyah":1,"toAyah":1,"webhookUrl":"https://x","webhookSecret":"s"}'
# {"status":"error","message":"Invalid API key","code":"AUTH_FAILED"}

# ٣) اختبار كامل من البداية للنهاية (webhook.site يعطيكم رابطاً يلتقط النتيجة)
curl -s -X POST $BASE/api/evaluate \
  -H "X-AI-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{
    "audioUrl": "https://everyayah.com/data/Husary_128kbps/112002.mp3",
    "surahNumber": 112, "surahName": "الإخلاص", "fromAyah": 2, "toAyah": 2,
    "userId": 1, "recitationId": 1,
    "webhookUrl": "https://webhook.site/<YOUR-ID>", "webhookSecret": "test-secret"
  }'
# {"status":"processing","jobId":"...","estimatedTime":30}
```

✅ **النجاح** = وصول الـ webhook إلى webhook.site بحالة `"status":"success"`، وأن يكون الحقل
`data.feedbackAudio` رابطاً من نوع **`https://cdn.quranyutla.com/feedback/...`** يعمل في المتصفح.

لمتابعة السجلّات: `modal app logs quran-ars` (ابحثوا عن `Grader container ready.`).

## ٧) التكلفة المتوقّعة

المحاسبة بالثانية، وفقط أثناء عمل الحاويات.

| المكوّن | متى يعمل | التسعيرة التقريبية |
|---|---|---|
| `web` (CPU، جاهز دائماً) | دائماً (`min_containers=1`) | **~٥–١٠ دولار/شهر** |
| `Grader` (GPU من نوع A10G) | فقط أثناء التصحيح | ~$0.000306/ثانية ← **~١.١٠ دولار/ساعة** |

عند **٢٥٠ تقييماً يومياً** (~١٠ ثوانٍ لكل تقييم ← ~٢١ ساعة GPU شهرياً) مع مهلة إطفاء ٦٠ ثانية:

- الـ GPU: **~٢٥–٤٥ دولار/شهر**
- حاوية الـ web الدائمة: **~٥–١٠ دولار/شهر**
- تخزين R2: **~١ دولار/شهر**
- **الإجمالي ≈ ٣٠–٥٥ دولار/شهر** (مقابل ~١٣٠–٣٢٠ دولار على RunPod Serverless لنفس الحِمل)

**لتوفير أكثر:** اضبطوا `min_containers=0` على `web()` لتوفير الـ ٥–١٠ دولار — عندها تستغرق أول
استجابة ~١–٢ ثانية فقط (الصورة صغيرة ولا تحتوي النموذج).

## ٨) ضبط الإعدادات

| الإعداد | مكانه | تأثيره |
|---|---|---|
| `scaledown_window=60` | `@app.cls` في `Grader` | مدّة بقاء الـ GPU جاهزاً بعد المهمة. ارفعوها إلى ١٢٠–٣٠٠ أثناء جلسة تجريب مكثّفة، أو خفّضوها إلى ~١٠ لأقل تكلفة. |
| `min_containers=1` | `@app.function` في `web` | يُبقي الواجهة فورية. اجعلوها ٠ لتوفير ٥–١٠ دولار مقابل تأخير ~١–٢ ثانية. |
| `gpu="A10G"` | `@app.cls` | `"L4"` أرخص وأبطأ، `"A100"` أسرع. **يجب أن يدعم bf16 — لا تستخدموا T4.** |
| `max_containers=3` | `@app.cls` | الحد الأقصى للتوازي؛ ارفعوه مع زيادة الحِمل. |
| `timeout=600` | `@app.cls` | أقصى زمن لمهمة تصحيح واحدة. |

## ٩) ملاحظات لفريق الباك-اند

- **الرابط الأساسي** = رابط `modal.run` من القسم ٥ (أو نطاقكم لاحقاً — القسم ١٠).
- **ترويسة المصادقة لم تتغيّر:** `X-AI-API-Key: <AI_API_KEY>`.
- **شكل الطلب والاستجابة والـ webhook مطابق تماماً** للعقد الموثّق في
  `BACKEND_HANDOFF.md` / `BACKEND_GUIDE_AR.md` — تغيير المنصّة **غير مرئي** بالنسبة لكم.
- **`webhookUrl` ما زال يُقرأ من جسم كل طلب** ولا يوجد أي رابط ثابت في الكود.
- **`feedbackAudio` صار رابط CDN** (`cdn.quranyutla.com/feedback/...`) بدل مسار داخل الخدمة —
  وهذا أفضل لكم: يُخدَّم مباشرة من التخزين، ولا يوقظ GPU، ويبقى محفوظاً.
- **الإقلاع البارد صار يؤخّر الـ webhook فقط** لا استجابة الـ API. يُفضّل مع ذلك أن يعرض التطبيق
  حالة «جاري التصحيح…»، لكن `/api/evaluate` نفسه يستجيب فوراً دائماً.

---

## ١٠) النطاق المخصّص (`ai.quranyutla.com`)

يدعم Modal النطاقات المخصّصة في الخطط المدفوعة (من لوحة التحكم → التطبيق → domains)، وهو أبسط من
حلّ Cloudflare Worker الذي كان مطلوباً مع RunPod. أو استخدموا نفس فكرة الـ Worker: توجيه
`ai.quranyutla.com/*` إلى رابط `modal.run`. وفي الحالتين **لا يمرّ الصوت عبره** — فهو يأتي مباشرة
من R2 عبر `cdn.quranyutla.com`.

وبما أن الباك-اند يحتفظ بـ `AI_SERVICE_URL` كمتغيّر بيئة، فإن الانتقال لاحقاً من رابط `modal.run`
إلى `ai.quranyutla.com` يكون بتغيير متغيّر واحد فقط دون أي تعديل في الكود.

## ١١) حلّ المشكلات

| العَرَض | الحل |
|---|---|
| `AUTH_FAILED` في كل الطلبات | قيمة `AI_API_KEY` في Secret الخاص بـ Modal لا تطابق الترويسة المُرسَلة. |
| الـ webhook لا يصل أبداً | راجعوا `modal app logs quran-ars`، وتأكّدوا أن `webhookUrl` متاح على الإنترنت العام. |
| `feedbackAudio` يعطي 404 | متغيّرات `S3_*` ناقصة أو خاطئة ← رجع الكود لمسار محلي غير موجود على Modal. راجعوا القسم ٤. |
| بطء أول عملية تصحيح | طبيعي (إقلاع بارد للـ GPU وتحميل النموذج). لا يؤثّر على استجابة الـ API بل على وقت وصول الـ webhook. |
| نص عربي مشوّه في المخرجات | النموذج **يجب** أن يعمل بدقّة bf16 — لا تستخدموا T4 ولا تفرضوا fp16. |
| فشل بناء الصورة عند `add_local_dir` | نفّذوا `modal deploy` من داخل مجلد `delivery/` (المسارات نسبية إليه). |

---

## ١٢) ملاحظة مهمّة بشأن أول عملية نشر

لم يكن بالإمكان تجربة النشر على Modal مسبقاً (لا يوجد حساب Modal على جهاز التطوير). الكود مُتحقَّق
من صحّته نحوياً ومن أنه يستدعي فقط دوالّ موجودة فعلاً في `main.py`، لكن **حزمة Modal تتغيّر بين
الإصدارات**، لذا قد يظهر خطأ أو اثنان في أول `modal deploy` (اسم مُعامل تغيّر مثلاً).

هذا أمر طبيعي في أول نشر ولا يعني وجود خلل. أرسلوا نصّ الخطأ ليُصحَّح فوراً.
